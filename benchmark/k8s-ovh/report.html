Operating Keycloak on Redis: Locke vs Infinispan

3-pod cluster · Keycloak 26.6.1 · production mode (start --optimized) · OVH · isolated load generator · 2026-05-24

Apache 2.0in-cluster runner

Locke is a Keycloak distribution that moves cluster cache coordination off embedded Infinispan/JGroups onto Redis. The question this benchmark answers is operational: can you run Keycloak at the same throughput, with better failure behavior, on a cache your cloud already manages?

Methodology

OVH Managed Kubernetes (BHS5), dedicated pool of 4× b3-64 (16 vCPU / 64 GB). 3 nodes run one Keycloak pod each (anti-affinity = a real 3-machine cluster); a 4th node runs the load generator + Postgres + Redis, isolated so results reflect the cache backend, not host contention. The full run was driven by an in-cluster runner pod (independent of any operator laptop).

  • A3 — Infinispan (vanilla KC 26.6.1): KC_CACHE=ispn, JGroups jdbc-ping (3-member view).
  • B3 — Locke 26.6.1: KC_CACHE=redis, realm/user/authz on Caffeine L1 + Redis pub/sub invalidation, sessions on JPA.
  • Both start --optimized, providers baked at build, identical resources (pinned 6 vCPU / 6 GB, -Xms2g -Xmx4g, DB pool 50), shared Postgres, same realm. Load = keycloak-benchmark Gatling AuthorizationCode flow, 60s/point, stacks sequential (idle stack scaled to 0).

Caveats: single region, dev-grade nodes, sequential runs. Phase Two figures later are their published numbers under their own conditions, not run by us.

2. Resilience — the operational win

This is the reason to move cache coordination off JGroups.

When an Infinispan node dies, the cluster stalls ~31–40 seconds doing JGroups rebalance + state transfer; requests hang into the tens of seconds. Locke keeps serving from Redis: p99 stays sub-second (1 down) to ~2.6s (2 down) — roughly 34× / 15× better p99. For an operator, that's "a pod restarted and nobody noticed" vs "auth latency hit 31s for half a minute."

3. Latency (steady state)

Honest read: Infinispan has lower p99 at moderate load — realm/user reads are in-process, while Locke adds a Redis round trip. Both stay under 170ms p99 to 250 users/sec (at the top of the range Locke is marginally lower). The small latency trade buys the resilience + ops gains above.

Placement is negligible below saturation (throughput identical, p99 within ~6–20ms). Locke's in-JVM L1 (Caffeine) absorbs most reads, so a managed/external Redis on the same network performs the same as colocated — no need to co-locate Redis with Keycloak.

5. Rolling version upgrade 26.3.5 → 26.6.1 under load

  • Vanilla (Infinispan): the rolling upgrade crosses an incompatible Infinispan/JGroups major (15 → 16). During the mixed-version window the cluster cannot form a unified view and requests hang indefinitely — effectively a cache-layer outage until all 3 pods land on 26.6.1 (~84s rollout).
  • Locke (Redis): rolls cleanly under load — no outage. Tested with properly-versioned Locke images (version.txt = 26.3.5 / 26.6.1 / 26.6.2), image flipped mid-stream under windowed load, fresh DB so the old version owns the schema.

Both complete gracefully — the only cost is a transient latency bump from the standard Keycloak DB migration as each new pod starts. Locke has no JGroups cluster-protocol version barrier, so the cluster never stalls the way Infinispan does. (An earlier attempt with a mislabeled 999.0.0-SNAPSHOT "26.3.5" image crash-looped — 26.6.1 refused the apparently-newer schema; a correctly-versioned 26.3.5 build fixed it.)

6. Adopting Locke: stock Keycloak → Locke migration (same version, under load)

The realistic adoption path — switch vanilla Keycloak 26.6.1 (Infinispan) to Locke 26.6.1 (Redis) without changing the Keycloak version (same DB schema), as a rolling image + cache-config change under load.

Baseline (Infinispan)204.8 rps · p99 73ms · 0 fail

Finding: adopting Locke at the same version lands cleanly at throughput parity; the live cutover has only a small, bounded disruption window driven by Infinispan's departure (not Locke). For a seamless switch, cut over in a brief maintenance window or drain pods one at a time. Far better than the cross-version Infinispan upgrade (a full outage).

Sessions are replicated in Infinispan, so moving them to Redis removes replication cost (faster). Realm/user caches are local, so moving them adds a round trip (slightly slower reads). Complementary, not competing. Their self-reported figures, not run by us.

Honest note: does Redis help Keycloak scale to many realms?

No, and we should say so. GET /admin/realms (list all) goes from 0.1s to minutes past a few hundred realms — identically on Infinispan and Locke. It is database + serialization bound, not cache bound (Keycloak discussion #11074). Locke's only realm-scaling effect is to bound the in-heap cache (predictable memory) rather than grow it. Realm-count scaling is a Keycloak/DB limit; Locke's value is operational.

Takeaways

  1. Throughput: a tie (~100%). Clustered Keycloak on Redis serves the same load, error-free, to saturation.
  2. Resilience: the win. A lost node costs Infinispan a ~31–40s rebalance stall; Locke keeps logins sub-second.
  3. Upgrades: Infinispan rolling upgrades across an incompatible JGroups version are an outage; Locke has no JGroups version barrier.
  4. Latency: a small, honest trade for the above. Redis does not change Keycloak's realm-count limits.
  5. Known gaps: bound the Redis client timeout (outage hangs in-flight requests, but recovers); ship a properly-versioned Locke 26.3.5 image for a clean upgrade measurement.
