Where do you run Redis for Locke?

A cross-backend comparison of cache options for the Locke (Keycloak-on-Redis) distribution: in-process Infinispan, co-located Redis (single & cluster), and two managed services — AWS ElastiCache and Azure Managed Redis — across throughput, full latency distributions, and failover.

The one-paragraph answer

Managed Redis is not all the same. AWS ElastiCache (an OSS Redis cluster you talk to directly, shard-by-shard) is a perfectly viable Locke backend — p99 181 ms at 80 logins/sec and a clean 522 ms through a node kill with zero errors. Azure Managed Redis (which funnels every request through a single managed proxy endpoint) is not — p99 4,940 ms at the same load, ~27× worse, for this write-heavy, multi-round-trip-per-login workload. Co-located Redis is fastest of the Redis options; in-process Infinispan has the lowest latency of all but stalls for 37 seconds on node loss — the failure mode Locke exists to remove.

1 · The managed-Redis verdict

The motivating question: is a managed Redis service as slow as Azure Managed Redis was? No — and the reason is architecture, not "managed vs self-hosted."

Everything except Azure Managed Redis sits under ~250 ms. AMR is alone at ~5 seconds. The difference is the data path: ElastiCache cluster-mode and co-located Redis are direct-to-shard OSS Redis — Locke's client opens one connection per shard and talks straight to it. AMR's working mode funnels all traffic through a single managed proxy endpoint, which amplifies badly under the concurrency of 850 logins/sec each doing several Redis round-trips. Per-operation, AMR is fine (~0.6 ms); it's the proxy funnel under load that hurts.

3 · Latency vs load

At 80 and 160 logins/sec every backend scales linearly to full throughput (273→547 rps) — the difference is purely latency. The shapes diverge as load climbs.

On the Azure rig (postgres and Redis on separate dedicated nodes) both Locke and Infinispan hold 250 ups at ~850 rps and p99 ≈ 100 ms. On the AWS rig they knee at 250 — which is the rig, not the backend (next section).

4 · Apples-to-apples honesty

What's clean and what isn't. The two rigs are not identical, so we only draw backend conclusions where the rig isn't the bottleneck.
  • The AWS 250-ups cliff is a rig artifact, not a backend property. On the AWS EKS cluster, postgres shares one node with the loadgen/infra tier and its write-ahead log sits on EBS gp3. At 250 ups (~850 session-persist writes/sec) every backend knees — including in-process Infinispan (rps 760, p99 4.6 s), which touches no Redis at all. On the Azure rig, with postgres on its own dedicated node, the identical software holds 250 ups at ~850 rps / 91 ms. Same code, different storage IOPS. We therefore compare backends at 80 and 160 ups, below that knee.
  • Topologies differ in size. "Co-located single redis" is one Redis thread; ElastiCache here is a 3-shard cluster; the Azure cluster is 6 nodes. A bigger deployment naturally absorbs more — that's why the 3-shard ElastiCache beats the single co-located Redis at 160 ups. It's a "what you'd actually deploy" comparison, not a same-size topology shoot-out.
  • Cross-cloud, and not the same CPU. ElastiCache ran on AWS; AMR and the Azure co-located reference ran on Azure. Both clouds used x86-64 with matched vCPU counts (16 KC / 8 aux) and the identical amd64 images, but different silicon: Azure E-series as_v7 is AMD EPYC, AWS c6i is Intel Xeon (Ice Lake). So cross-cloud absolute latencies carry three confounds at once — CPU vendor, storage (Azure premium SSD vs AWS EBS gp3), and node placement (separate vs shared infra node). The managed-proxy-vs-direct-shard contrast is architectural and dwarfs these; the clean same-CPU backend comparison is the AWS-only set at 80/160 ups.
  • Workload. keycloak-benchmark Gatling AuthorizationCode (full login → code → token). Steady-state authentication only — the harness does not continuously create users while authenticating. 3 KC pods, start --optimized, Keycloak 26.6.x.

5 · Resilience — the reason Locke exists

Throughput parity and a few ms of latency are the price; resilience is what you buy. A single KC pod is killed mid-run at T+43s.

Infinispan's in-process cache must rebalance its JGroups cluster on membership change: p99 jumps to 37 seconds and stays elevated for ~65s before recovering — a 0.68% error window. Locke holds p99 at 268 ms (Azure co-located) / 522 ms (AWS ElastiCache) with effectively zero errors: cache state lives in Redis, so losing a stateless KC pod is a non-event. That's a ~140× smaller failover impact.

6 · Recommendations

  • Best latency + resilience: co-located Redis (a small cluster on the same nodes/VPC). Sub-100 ms p99 to 250 ups and sub-100 ms failover.
  • Already run managed Redis? AWS ElastiCache (or any OSS cluster-mode service you talk to directly) is viable. Budget the network-hop latency (p50 ~5→55 ms vs in-process) and size the tier for your peak — and keep Redis in the same VPC/AZ as Keycloak.
  • Avoid single-proxy-endpoint managed Redis (Azure Managed Redis in its OSS/Enterprise-cluster working mode) for this workload — the proxy funnel amplifies multi-round-trip logins into seconds of p99.
  • Don't keep Infinispan for HA. It's the latency floor but a 37-second failover stall is disqualifying for zero-downtime operation — which is the whole point of Locke.
